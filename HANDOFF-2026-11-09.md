## 1. Where things stand

Vendavis is a desktop Salesforce metadata explorer built with Tauri v2. It lets developers and admins inspect field-level security, profiles and permission sets, run SOQL, execute Apex, and audit org health from a native app. An AI assistant tab gives natural-language Salesforce help through a configurable provider.

| | |
|---|---|
| App / version | Vendavis 2.0.0 (MVP 0) |
| Shell | Tauri v2 (Rust) |
| Frontend | React 18 + Vite + Tailwind CSS |
| Backend | Python FastAPI + uvicorn, bundled with PyInstaller as `sf_backend` |
| AI layer | Provider-agnostic via `opencode.config.json` + OpenAI-compatible SDK (`openai`) |
| SF CLI | `@salesforce/cli` (`sf` / `sfdx`) — must be installed by the user |
| Dev port | 7891 (production: free port, injected as `window.__SF_BACKEND_PORT__`) |

### What changed since the previous handoff

1. **The `@opencode/sdk` task was dropped.** The original handoff assumed it was an OpenAI-style chat client. It is not — see [section 4](#4-decision-opencode-sdk-not-used-for-chat).
2. **Windows support was added** and verified (section 5).
3. **`backend/sf_backend.spec` was recreated** and is now tracked in git (section 6).
4. **`requirements.txt` fixed:** it still listed `anthropic` while `ai_client.py` imports `openai`, so the backend crashed on startup. It now lists `openai`, plus `lxml` (used by `excel_builder.py` for checkbox injection, previously undeclared).

## 4. Decision: `@opencode/sdk` not used for chat

The previous handoff proposed wiring `@opencode/sdk` into `ClaudeChat.jsx` to replace the raw SSE call to `/api/ai/chat`. After reading the docs (<https://opencode.ai/docs/build/sdk/> and <https://opencode.ai/docs/build/client/>) this does not work:

- **`@opencode/sdk`** *embeds the whole OpenCode server in-process* (sessions bound to directories, worktrees, plugins, agents). It needs a Node/Bun/Workers runtime — it cannot run in a Tauri WebView — and it has no `apiKey`/`baseURL` options. Providers are configured inside OpenCode.
- **`@opencode/client`** is the browser-compatible network client, but it talks to a running `opencode serve` using `session.create` / `session.prompt`. It is a coding-agent API, not chat completions, and it brings file/shell tools that would need locking down.

**Decision:** keep the Python backend proxy. `ai_client.py` already supports OpenAI, Anthropic-compatible, Azure, Ollama, OpenRouter and any OpenAI-compatible gateway. `@opencode/sdk` was removed from `frontend/package.json`.

If agent features are wanted later, the realistic path is `@opencode/client` against a managed local `opencode serve` sidecar — a separate project, not a drop-in replacement.

### Current AI architecture

Config priority in `ai_client.py` (highest first):

1. `opencode.config.json` in project root (developer override)
2. `OPENCODE_API_KEY` / `OPENCODE_BASE_URL` / `OPENCODE_MODEL` env vars
3. `~/.vendavis_api_key` (written by the Settings modal)
4. `~/.vendavis_config.json` (`model`, `base_url`)
5. Legacy `~/.sf_tools_config.json`; legacy `~/.anthropic_key` still read as a fallback

Endpoints: `POST /api/ai/chat` (active), `POST /api/claude/chat` (compat alias). Frontend call sites are in `ClaudeChat.jsx` (`apiStream("/api/ai/chat", …)`).

## 5. Windows support

Developed and tested on Windows 11 (Node 24, Python 3.12, Rust stable MSVC).

| Area | Implementation | Verified |
|---|---|---|
| Process cleanup | `platform.rs`: process-wide Job Object with `KILL_ON_JOB_CLOSE`; child assigned in `on_spawned`; `TerminateJobObject` on shutdown. Also `CREATE_NO_WINDOW`. | `cargo test` — grandchild process is killed with the tree |
| Why it matters | A PyInstaller one-file build runs a bootloader **and** a Python child (2 processes). `child.kill()` alone would orphan the worker. | Observed 2 `sf_backend` processes |
| `sf` discovery | `WindowsProvider` asks `npm prefix -g`, checks `C:\Program Files\sf\bin`, `%LOCALAPPDATA%\sf\bin`, `%APPDATA%\npm`, Volta | `/api/sf-version` resolves `sf.CMD` |
| Subprocess output | `SUBPROCESS_KWARGS` in `sf_cli.py`: UTF-8 decoding + `CREATE_NO_WINDOW` | Backend runs |
| Paths | `main.rs`: `Scripts\python.exe` and `sf_backend.exe`; `libc` is Unix-only, `windows-sys` for Windows | `cargo check`, no warnings |
| npm scripts | `scripts/venv-run.mjs` replaces hard-coded `.venv/bin/...` | `uvicorn` starts via script |
| Bundling | `tauri.windows.conf.json` nulls `sf_backend`, adds `sf_backend.exe` | `cargo check` resolves resource |

### Release build (verified 2026-11-09)

`npm run tauri:build` succeeds on Windows and produces two installers in `src-tauri/target/release/bundle/`:

- `msi/Vendavis_2.0.0_x64_en-US.msi` (~26 MiB)
- `nsis/Vendavis_2.0.0_x64-setup.exe` (~26 MiB) — per-user, no admin needed, installs to `%LOCALAPPDATA%\Vendavis`

Checked on the NSIS-installed app, launched from an unrelated working directory:

- Window opens ("Vendavis - Unofficial Salesforce Tool"); the bundled `sf_backend.exe` (next to the app exe) starts on a dynamically allocated port.
- `/api/sf-version` and `/api/orgs` respond; the three orgs authorized in the local `sf` CLI are listed.
- Killing the app abruptly (`Stop-Process -Force`, bypassing `confirm_close`) also kills both backend processes and frees the port — the Job Object works end to end.

Silent install/uninstall: `Vendavis_2.0.0_x64-setup.exe /S`, then `%LOCALAPPDATA%\Vendavis\uninstall.exe /S`.

### Not yet verified on Windows

- **Interactive use of the UI against a real org** — FLS export, SOQL, Apex, Org Health and the AI chat (needs a key in Settings). Only the API layer was exercised.
- **`npm run dev`** (Vite + uvicorn + Tauri in dev mode).
- The MSI installer (per-machine, needs admin) — only NSIS was installed.
- Code signing: installers are unsigned, so SmartScreen will warn. Auto-update is not configured.
- Linux has providers in code but is untested.

## 6. Backend build (`sf_backend.spec`)

`backend/sf_backend.spec` was previously gitignored and missing, so `npm run build:backend` could not run. It is now tracked (the `backend/*.spec` ignore rule was removed).

- One-file build → `backend/dist/sf_backend` (`sf_backend.exe` on Windows, ~25 MB).
- `collect_submodules("uvicorn")` is required: uvicorn selects loops/protocols by string name at runtime.
- `lxml`, `openpyxl`, `sqlite3` are listed as hidden imports (lazy imports).
- `anthropic`, `tkinter`, `pytest` are excluded.
- `console=True` is intentional: uvicorn logs to stdout/stderr, which are `None` in a windowed build. The Rust launcher hides the window on Windows.
- Smoke-tested: the built exe serves `/api/sf-version` and `/api/settings`.

**Gotcha:** Tauri's build script requires the bundled resource to exist even in dev. If `cargo check` fails with ``resource path `..\backend\dist\sf_backend.exe` doesn't exist``, run `npm run build:backend` once (or create an empty placeholder file; `backend/dist/` is gitignored).

## 7. Key technical decisions and gotchas

- **Tauri v2 permissions.** The capabilities file must list `core:event:allow-listen` and `core:event:allow-emit` explicitly. `core:event:default` does not exist in v2 and silently breaks event dispatch.
- **Async Tauri commands with `State`.** Commands borrowing `State<'_>` must return `Result<T, E>`. `confirm_close` returns `Result<(), ()>`.
- **macOS SF CLI path.** Bundled `.app` gets a minimal PATH. `MacOSProvider` runs `npm root -g`, finds `node` next to `npm`, and prepends it so the `sf` shebang (`#!/usr/bin/env node`) resolves.
- **Unix process cleanup.** `setsid()` in `pre_exec` + `killpg(SIGKILL)` (`UnixPlatform`).
- **Expired Salesforce sessions.** If an org's refresh token is dead, every live API call fails. `sf_cli._sf` and `get_org_limits` raise `SessionExpiredError`; `main.py` turns it (even when wrapped by the many `except Exception → HTTPException(500)` blocks, via `__context__`) into `401 {"code": "session_expired", "detail": "... run sf org login web --alias X"}`. Rust (`http_error`) and `client.js` pass that message through unmodified. `get_org_limits` first forces a token refresh and retries once, since a stale 2-hour access token with a valid refresh token is recoverable. The refresh-success path is untested (all local orgs were fully expired when this was written).
- **`sf` exit code 2** means "warning" (e.g. update available) even on success; `sf_cli.py` parses stdout JSON first.
- **Flock icon** is generated from the original 512×512 PNG with Pillow (script not checked in): extract white pixels, composite three copies at scales 1.0/0.64/0.44 and opacities 1.0/0.48/0.18, stacked vertically on navy `#1a2d5a`. `public/` versions have no background.
- **Directory name.** The project began as `sf-metadata-exp-electron`; names like `sf-metadata-explorer` remain in `package.json` / `Cargo.toml`.
- **Line endings.** Git on Windows warns about LF→CRLF; harmless.

## 9. Dev environment setup

### Prerequisites

- Node.js 18+ and npm
- `@salesforce/cli` — `npm install -g @salesforce/cli`
- Python 3.9+
- Rust (rustup) with Tauri prerequisites:
  - **Windows:** Visual Studio 2022 Build Tools with the *Desktop development with C++* workload; WebView2 (preinstalled on Windows 11)
  - **macOS:** Xcode command line tools

Tauri CLI is installed as an npm dev dependency; no `cargo install tauri-cli` needed.

### Install

```sh
npm install                    # root deps; postinstall also runs `npm install` in frontend/
cd backend
python -m venv .venv
```

Activate and install:

```sh
# macOS / Linux
source .venv/bin/activate
# Windows (PowerShell)
.\.venv\Scripts\Activate.ps1

pip install -r requirements.txt pyinstaller
```

> On Windows, open a **new** terminal after installing Rust so `cargo` is on PATH. If `python` opens the Microsoft Store, use `py -3.12` or disable the App execution alias.

### Run

```sh
npm run dev            # Vite + uvicorn (port 7891) + Tauri
npm run dev:backend    # backend only (works on any OS via scripts/venv-run.mjs)
```

### Build

```sh
npm run tauri:build    # PyInstaller (sf_backend) then tauri build
```

### Tests

```sh
cd src-tauri && cargo test     # Windows: Job Object kill-tree test
```
